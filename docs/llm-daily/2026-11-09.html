1. LeCun 新论文正面挑战 Scaling Law：1.09 亿参数的文本 JEPA，在跨模态表征对齐上胜过 720 亿的 Qwen2.5

一句话概要： 图灵奖得主 Yann LeCun 与布朗大学助理教授 Randall Balestriero 联合发表 37 页论文，在"柏拉图表征假说"基础上建立数学框架，论证"预测下一个 token"这条路线在学到世界表征上是低效的，并给出替代方案：参数量仅 1.09 亿的文本 JEPA，在跨模态表征对齐任务上超过 720 亿参数的 Qwen2.5。

技术要点： 论文的核心不是"小模型也能打"，而是回答一个更基础的问题——不同模态（文本、图像、视频）的模型，能否学到同一套"世界表征"。作者把柏拉图表征假说推进为可证明的数学框架：只要训练时正样本之间满足特定的关系约束（同一语义的不同模态/不同视角互为正样本），JEPA 类模型学到的表征之间就只差一个旋转变换，即可以通过正交变换相互对齐。这一步把"表征对齐"从经验观察变成了可推导的性质，也解释了为什么目标驱动（预测表征而非预测像素/token）的训练方式，样本效率会显著更高。

实验结果： 论文报告两项关键数字：其一，1.09 亿参数的文本 JEPA 在跨模态表征对齐测试中超过 720B 的 Qwen2.5，参数差距约 660 倍；其二，换用该训练方法后，达到同等对齐效果所需的训练样本量降到原来的约 1/42。作者同时从数学上论证了 next-token 预测路线的效率损失来源：token 级目标把大量容量花在了不可预测的细节上，而非稳定的语义结构。

影响分析： 这并不等于"大模型要凉"。论文评测的是表征对齐这一项能力，不是通用生成、推理或工具调用；而 Qwen2.5-72B 也并非为跨模态对齐专门训练。真正值得工程侧注意的是它给出的方向性判断：训练目标的选择可能比参数规模更决定"效率"。对一线团队，这意味着三件事——一是做多模态检索、跨模态召回这类任务时，不必默认上大模型，任务对齐的目标函数 + 中等规模编码器可能更划算；二是评估供应商时应区分"参数量"与"有效表征容量"，后者才决定下游微调成本；三是若 JEPA 路线在视频、具身场景继续被验证，"世界模型"与"语言模型"的分工会进一步明确，而不是所有能力都塞进一个 decoder-only 架构。

2. 腾讯混元 Hy4 正式版：770B 总参数 / 49B 激活，首次"看图 + 操作电脑"，权重近期开源

一句话概要： 11 月 4 日腾讯在乌镇峰会发布混元 Hy4 正式版，MoE 架构总参数 770B、每 token 激活 49B、上下文 1M，首次引入原生视觉理解与电脑操作（GUI/CLI）能力，官方称进入全球开放权重第一梯队，权重将于近期开源，接入 WorkBuddy 后调用量激增、推理集群紧急扩容十倍。

技术要点： 规格与 8 月底的 Hy4 preview 一致（770B/49B/1M），真正的新增是两项能力。其一是视觉理解：把感知、推理与工具调用串起来，覆盖细粒度图像处理、复杂图表解读、文档理解、多图联合分析和带图数学推理；官方演示中模型能在 28 亿像素航拍图里定位目标。其二是电脑操作：可解读屏幕内容并移动鼠标、点击、填表，操作图形界面与命令行工具。相比上一代 Hy3（总参数 295B、激活 21B、上下文 256K），Hy4 总参数扩大到约 2.6 倍。

实验结果与成本： preview 阶段公布的 Terminal Bench 2.1 得分 85.4，是其在命令行工作流上的主要硬指标；正式版官方未单列新跑分，更强调"能干活"的交付体验。定价保持 preview 口径：输入 6 元、输出 18 元每百万 token，缓存命中 0.3 元；TokenHub 侧到 12 月 31 日按刊例价五折，WorkBuddy、CodeBuddy、元宝与企业微信智能助理"大圆"已接入。

影响分析： Hy4 的定位是"生产力模型"，其 MoE 结构（知识容量由 770B 决定、单次计算量由 49B 决定）给出了一条可复用的成本公式：用总参数买能力上限，用激活参数买推理毛利。对国内做私有化或行业 Agent 的团队，1M 上下文 + GUI 操作意味着"整份标书/整套后台系统"可以一次性喂进去，而不必先做复杂的 RAG 切分与工具封装——这既是机会也是风险：上下文越长，提示注入与越权操作的攻击面越大，上线前必须补上操作白名单与人工确认环节。

3. 阿里开源 Qwen3.8 全系：旗舰 2.4 万亿参数，CodeArena 登顶、Text Arena 全球第五

一句话概要： 阿里通义千问开源 Qwen3.8 系列，形成"旗舰 Max + 27B 多模态主力 + Flash 轻量"的三层矩阵，旗舰总参数 2.4 万亿、激活 95B、支持 1M 上下文，Qwen3.8-Max 在 Text Arena 位列全球第五（紧随 Claude 系列），CodeArena 前端编程总榜登顶，27B 版本登上 Hugging Face 趋势榜（超 1.9 万赞、760 万次下载）。

技术要点： 这是 Qwen 首次把 Max 级旗舰开放权重，延续稀疏 MoE + 超长上下文的路线：2.4T 总参数决定知识与能力上限，95B 激活把单次推理成本压到可商用区间；27B 版本承担多模态主力，覆盖图文理解与视觉推理；Flash 版本面向高吞吐低成本场景。三层矩阵的设计意图很明确——用同一个家族覆盖"最强 / 最均衡 / 最便宜"三种采购决策，降低企业选型与迁移成本。

实验结果： 第三方榜单是主要证据：Text Arena 综合性能居全球第一梯队，Vision Arena 视觉榜第二，CodeArena 前端编程总榜排名继续上升并登顶；27B 在 Hugging Face 的下载量（760 万次）说明社区侧的部署意愿，而不只是榜单热度。

影响分析： 一周内 2.4T（Qwen3.8）与 2.8T（Kimi K3.1 Pro）两个万亿级开放权重先后落地，意味着"万亿参数"从闭源卖点变成了开源基线。对国内团队的直接后果是选型逻辑变化：过去"开源=能力打折"，现在开源旗舰已能进第一梯队，采购谈判的重心从"能不能用"转向"许可证条款、推理成本、微调工具链"。需要提醒的是，开放权重不等于开源——商用条款、品牌标注、收入门槛等限制正在分层，法务评估不能省。

来源： 阿里云开发者社区 ｜ AI 资讯日报 11-08

4. OpenAI 110 亿美元融资落地，估值让步至 1.25 万亿美元；微软被曝收缩算力租赁、退出甲骨文云协议

一句话概要： 路透报道 OpenAI 完成新一轮融资首批约 110 亿美元交割，投后估值 1.25 万亿美元，低于最初寻求的 1.5 万亿美元；同周微软被曝收缩 AI 算力租赁并逐步退出与甲骨文的云协议，摩根大通副董事长公开提示 AI 板块估值仍高、将出现回调。

关键事实： 首批资金由软银、MGX 等出资，本轮计划募资规模报道存在 200 亿与 300 亿美元两种口径（路透口径为上限 300 亿），当前到账仅约三分之一。公司 CFO 称三季度业务环比增长 70%、企业客户需求翻倍。另一边，微软的算力策略从"抢产能"转向"调结构"：收缩对外 AI 算力租赁、逐步退出甲骨文云协议，同时继续自建数据中心。

为什么重要： 这是 2026 年下半年第一次出现"资本与算力同时校准"的组合信号。融资端，估值从 1.5 万亿退到 1.25 万亿，说明一级市场对"远期 AGI 叙事"的折价开始显性化；算力端，微软作为最大买方之一主动收缩租约，意味着此前"锁产能—抬估值—再融资"的循环出现松动。两端叠加，指向同一个问题：AI 基础设施的投入正在从"信仰驱动"切换到"现金流驱动"。

影响分析： 对使用方而非投资方，这件事的实际含义是供应链稳定性风险上升。过去两年企业采购模型服务时，默认假设是"供应商算力无限、价格持续下降"；当头部厂商开始调整租约与产能，模型 API 的限流、涨价、区域可用性波动都可能出现。建议在架构上保留多供应商路由（同一任务可在 2-3 家模型间切换）、把关键能力做本地或私有化兜底，并在合同里明确 SLA 与价格调整条款。至于"AI 泡沫"判断，更稳妥的观察指标不是估值，而是推理侧的真实调用量与付费留存——本周 175 万亿日均词元的数字，恰好是这条曲线的正面证据。

来源： 路透社报道（抖音转述） ｜ 钛媒体数智周报 ｜ AI 资讯日报 11-09

5. 中国 AI 推理量首次超过训练量：日均 175 万亿词元，DeepSeek Harness 日活 154 万

一句话概要： 行业统计显示中国 AI 推理数据量首次超过训练量，日均词元调用超 175 万亿；开源智能体框架 DeepSeek Harness 单日活跃用户达 154 万、日均消耗 92 万亿 token、第三方插件 3.5 万个；腾讯 WorkBuddy 累计完成 90 亿次任务请求，2026 年中国智能体市场规模预计 135.3 亿元、增速超 70%。

技术要点： 推理量超过训练量，是"模型从研发品变成消费品"的分水岭。它带来三个工程后果：其一，成本结构反转——训练是一次性资本开支，推理是持续性运营开支，优化目标从"更快训完"变成"每 token 更便宜"；其二，负载形态变化——训练是长时高吞吐批处理，推理是短时高并发、长尾分布，对 KV Cache 管理、批调度、投机解码的要求完全不同；其三，架构重心迁移——MoE 稀疏激活、前缀缓存、量化与端侧推理成为主战场（本周 Hy4 与 Qwen3.8 的定价、淘宝 MNN-Pocket-0.3B 的端侧发布都是同一逻辑的产物）。

数据解读： 175 万亿/日与 92 万亿（Harness 单一框架）这两个数字需要谨慎看待：前者来自行业口径，后者来自单一产品自报，二者统计边界不同，不宜直接相减推算份额。但它们共同说明"Agent 调用"已成为 token 消耗的主要来源——一次 Agent 任务动辄数十次模型调用与工具往返，其消耗量级远高于单轮对话。这也是为什么"按任务完成计费"开始替代"按席位订阅"。

影响分析： 对一线运维与平台团队，最现实的变化是容量规划方法要改。过去按"峰值 QPS"扩容，现在要按"token/秒 + 上下文长度分布"建模：长上下文请求会把 KV Cache 显存占用推到主导地位，一个 1M 上下文的请求可能顶掉几十个短请求的并发。建议监控三个指标——P99 首 token 延迟、缓存命中率、每千 token 单位成本，并用"短请求优先 + 长请求排队"的混部策略替代单一队列。另一个被低估的点是插件生态：3.5 万个第三方插件意味着权限治理必须前置，否则一次恶意插件调用就可能把内部数据带出去。
