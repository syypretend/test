Trie 树

类别：数据结构 | 难度：中等

算法简介

Trie 树（发音同 "try"），又称前缀树、字典树、单词查找树，是一种专门用于存储和检索字符串集合的多叉树结构。它的核心思想是：利用字符串的公共前缀来节约存储空间，将具有相同前缀的字符串共享同一条路径，从而实现极快的前缀匹配。

Trie 的每个节点代表一个字符（或字符的累积），从根节点到任意节点的路径拼接起来就是一个字符串前缀。每个节点包含两个核心组件：children（子节点映射，记录下一个字符到子节点的对应关系）和 is_end（布尔标记，表示从根到该节点是否构成一个完整单词）。

Trie 的查询时间复杂度与字符串长度成正比（$ O(L) $），而与集合大小无关，这是它区别于哈希表（平均 $ O(1) $ 但常数大、无前缀能力）和二叉搜索树（$ O(L \cdot \log n) $）的核心优势。它广泛应用于搜索引擎自动补全、拼写检查、敏感词过滤、IP 路由（最长前缀匹配）等场景。

原理示意图

数学公式

1. 查询/插入/删除时间复杂度

$$ T_{\text{op}} = O(L) $$

变量解释：

  • $ L $：被操作字符串的长度
  • 含义：三种核心操作都只需从根节点沿路径最多走 $ L $ 步，每步在 children 中做一次映射查找。与集合中存储了多少个单词无关，这是 Trie 的核心优势

2. 空间复杂度

$$ S = O\left(\sum_{w \in \mathcal{W}} |w| \times \text{sizeof(Node)}\right) \approx O(N \cdot \bar{L} \cdot |\Sigma|) $$

最坏情况（无公共前缀，所有字符串互为"前缀不共享"）：

$$ S_{\text{worst}} = O(N \cdot L \cdot |\Sigma|) $$

变量解释：

  • $ \mathcal{W} $：存储的单词集合
  • $ |w| $：单词 $ w $ 的长度
  • $ N $：单词总数
  • $ \bar{L} $：平均单词长度
  • $ |\Sigma| $：字符集大小（小写字母为 26，ASCII 为 128，Unicode 为全部字符）
  • 含义：若用数组存储 children（每个节点 $ |\Sigma| $ 个指针槽位），空间开销大；若用字典/哈希表存储 children，空间仅为实际出现的字符，最坏 $ O(N \cdot L) $

3. 前缀共享节省率

$$ \text{节省率} = 1 - \frac{\text{Trie 节点数}}{\sum_{w \in \mathcal{W}} |w|} $$

变量解释：

  • 节点数 = 去重后的所有前缀数量（含根）
  • $ \sum |w| $ = 所有单词字符总数（朴素存储）
  • 含义：前缀重合度越高，节省率越高。例如 "card/cardiology/cards" 三个词共 18 个字符，但 Trie 中仅需 12 个节点

核心要点

  • 用空间换时间：公共前缀共享路径，查询复杂度 $ O(L) $ 与词库规模无关
  • 每个节点两大组件：children（字符→子节点映射）+ is_end（完整单词结尾标记）
  • search 与 startsWith 的关键区别：前者必须走到尾且 is_end=True，后者只需路径存在
  • 查询稳定性极好：无哈希冲突问题，最坏也是 $ O(L) $，不像哈希表有退化风险
  • 三种典型实现：数组式（快、费内存，适合定长字符集如 a-z）、字典式（省内存、支持任意字符）、双数组/AC 自动机（工程优化版）
  • 大量前缀敏感场景的首选：自动补全、拼写检查、敏感词过滤（配合 DFS/AC 自动机）、IP 路由最长前缀匹配

技术细节与参数详解

#### 参数1：children（子节点容器）

  • 含义：存储当前节点的所有子节点，键为下一个字符，值为子节点对象。是 Trie 的核心结构参数
  • 类型：数组 / 字典（哈希表） / 链表
  • 默认值：视实现而定。数组式通常为 None 数组（长度=字符集大小）；Python 常用 dict（空字典）
  • 取值范围：
  • 数组式：固定长度 $ |\Sigma| $ 的数组（a-z 为 26）
  • 字典式：任意大小的哈希表
  • 对结果的影响：
  • 数组式：查找 $ O(1) $ 且无哈希计算，但每个节点占用 $ |\Sigma| $ 个指针位，内存开销大（26 指针 × 8 字节 = 208 字节/节点）
  • 字典式：只存实际出现的字符，内存省，但查找有哈希开销（常数变大），且字符集不受限（可存中文、emoji）
  • 推荐设置：字符集小且固定（如纯小写英文）用数组式；字符集大或不确定（中文、URL、代码 token）用字典式

#### 参数2：is_end（单词结尾标记）

  • 含义：布尔标记，表示"从根节点到当前节点的路径"是否构成一个完整的、被存储的单词
  • 类型：布尔值
  • 默认值：False（新节点默认不是单词结尾）
  • 取值范围：True / False
  • 对结果的影响：
  • is_end=True：该节点同时可拥有子节点（如 "car" 是词且 "card" 也是词）
  • search("car") 只查路径存在不查 is_end 会导致误报：把 "ca"（仅是前缀）当成已存储的词
  • 推荐设置：必须使用。这是 search 与 startsWith 区分的唯一依据，丢失它 Trie 语义就不完整

#### 参数3：字符集大小 |Σ|（alphabet size）

  • 含义：Trie 中允许出现的字符总数，决定数组式 children 的长度
  • 类型：整数
  • 默认值：LeetCode 208 题设为 26（仅小写 a-z）
  • 取值范围：26（小写） / 52（含大小写） / 128（ASCII） / 256（扩展 ASCII） / 65536+（Unicode）
  • 对结果的影响：$ |\Sigma| $ 越大，数组式实现的每个节点内存越大（线性增长）；超过 256 后数组式不再实用，必须改字典式
  • 推荐设置：英文场景 26 或 128；中文/多语言场景用字典式，不设固定大小

#### 参数4：大小写敏感策略（case handling）

  • 含义：是否在插入/查询前统一字符大小写（如全部 lowercase）
  • 类型：布尔/枚举
  • 默认值：敏感（不转换）
  • 取值范围：不转换 / 全转小写 / 全转大写
  • 对结果的影响：
  • 不转换："Apple" 和 "apple" 是两个不同的词（占两条路径）
  • 转小写：二者视为同一词，节省空间但丢失语义区分（人名场景不适合）
  • 推荐设置：敏感词过滤、自动补全等通常统一小写；编程语言关键字/标识符检索必须保持敏感

#### 参数5：节点值/权重（node value / weight）

  • 含义：给节点附加数据，如词频（用于热门词排序）、子树叶子计数（用于补全排序）、指向业务数据的引用
  • 类型：任意（整数词频 / 对象引用）
  • 默认值：无
  • 取值范围：视业务需求
  • 对结果的影响：附加词频后，自动补全可按热度返回 Top-K 而非字典序；附加子树计数可 $ O(1) $ 判断某前缀下有多少词
  • 推荐设置：自动补全场景强烈建议加 count 字段；纯存在性查询可省略

#### 参数6：压缩开关（compression，如 Radix Tree）

  • 含义：将只有单链分叉的路径合并为单节点存储多字符（Patricia/Radix 树）
  • 类型：布尔/策略
  • 默认值：不压缩（标准 Trie）
  • 取值范围：不压缩 / 路径压缩（Radix Trie）
  • 对结果的影响：
  • 不压缩：插入/删除实现简单，但单链节点浪费内存（如 "cardiology" 造成 10 个只有 1 个子节点的节点）
  • 压缩后：内存大幅减少，但节点需存字符串片段、边界字符比较更复杂（需要按片段而非单字符匹配）
  • 推荐设置：教学/面试/一般场景用标准 Trie；海量字符串（千万级）存储用压缩 Trie

#### 参数7：fail 指针（AC 自动机扩展）

  • 含义：Aho-Corasick 自动机在 Trie 基础上为每个节点加 fail 指针，指向"当前字符串的最长后缀对应的节点"，实现多模式串一次扫描
  • 类型：节点指针
  • 默认值：无（标准 Trie 无此参数）
  • 取结果的影响：加 fail 指针后，敏感词过滤从"逐模式串查询"变为"文本单遍扫描即完成所有模式匹配"，复杂度从 $ O(\text{模式串数} \times L \times N) $ 降为 $ O(N + \text{匹配次数}) $
  • 推荐设置：单一前缀查询用标准 Trie；多模式串同时匹配（敏感词、病毒特征码）必须用 AC 自动机

代码示例

class TrieNode:
    """Trie 节点类"""
    def __init__(self):
        self.children = {}    # 子节点映射：{字符: TrieNode}，字典式实现省内存且支持任意字符
        self.is_end = False   # 单词结尾标记：True 表示从根到该节点构成一个完整单词


class Trie:
    """前缀树（字典树）标准实现：insert / search / startsWith 三大核心操作"""
    def __init__(self):
        self.root = TrieNode()   # 根节点不存字符，仅作为入口


    def insert(self, word: str) -> None:
        """插入单词 word：逐字符沿树下行，不存在则建新节点，末节点 is_end 置 True"""
        node = self.root                       # 从根节点出发
        for ch in word:                        # 遍历单词的每个字符
            if ch not in node.children:        # 当前字符对应的子节点不存在
                node.children[ch] = TrieNode() # 创建新子节点
            node = node.children[ch]           # 移动到子节点，继续处理下一字符
        node.is_end = True                     # 到达单词末尾，标记为完整单词


    def search(self, word: str) -> bool:
        """查询单词 word 是否被完整存储：必须走到尾且 is_end=True"""
        node = self._find_node(word)           # 沿路径查找最后一个字符对应的节点
        return node is not None and node.is_end # 路径存在 且 是单词结尾 → 找到


    def startsWith(self, prefix: str) -> bool:
        """查询是否存在以 prefix 为前缀的单词：只需路径存在，不要求 is_end"""
        return self._find_node(prefix) is not None  # 节点存在即有此前缀


    def _find_node(self, s: str):
        """辅助方法：沿字符串 s 对应的路径下行，返回终点节点；路径中断返回 None"""
        node = self.root                       # 从根节点出发
        for ch in s:                           # 逐字符匹配
            if ch not in node.children:        # 字符无对应子节点 → 路径中断
                return None                    # 前缀不存在
            node = node.children[ch]           # 移动到下一节点
        return node                            # 返回终点节点（可能为 None）

    def autocomplete(self, prefix: str, limit: int = 10) -> list:
        """自动补全：返回所有以 prefix 开头的单词（DFS 收集子树所有单词）"""
        start = self._find_node(prefix)        # 定位前缀终点节点
        if start is None:                       # 前缀都不存在，无补全结果
            return []
        results = []                           # 收集补全候选词
        self._dfs_collect(start, prefix, results, limit)  # DFS 遍历子树
        return results

    def _dfs_collect(self, node, path, results, limit):
        """DFS 收集子树中的所有完整单词（可加词频排序，此处按字典序）"""
        if len(results) >= limit:              # 已达数量上限，剪枝返回
            return
        if node.is_end:                        # 当前节点是完整单词结尾
            results.append(path)               # 收入结果集
        for ch in sorted(node.children):       # 按字符顺序遍历（保证字典序输出）
            self._dfs_collect(node.children[ch], path + ch, results, limit)


# 使用示例
trie = Trie()                                  # 创建 Trie
for w in ["cat", "car", "card", "dog", "door", "done"]:
    trie.insert(w)                             # 批量插入单词
print(trie.search("car"))                     # True（完整存储的词）
print(trie.search("ca"))                       # False（只是前缀，非完整词）
print(trie.startsWith("ca"))                   # True（存在 ca 开头的词）
print(trie.autocomplete("do"))                 # ['dog', 'done', 'door']

复杂度分析

时间复杂度：

操作复杂度推导
insert$ O(L) $每字符一次 children 查找+移动，共 $ L $ 次
search$ O(L) $同上，末尾多一次 is_end 判断
startsWith$ O(L) $同 search 但不判 is_end
自动补全$ O(L + \text{子树大小}) $定位前缀 $ O(L) $ + DFS 收集整个子树
删除$ O(L) $下行定位 + 回收无分支节点

空间复杂度：字典式 $ O(\sum|w|) $ 最坏无共享时；实际由去重前缀数决定，公共前缀越多越省。数组式为 $ O(\sum|w| \cdot |\Sigma|) $。

对比推导：二叉搜索树存 $ N $ 个词查一个词需 $ O(L \cdot \log N) $（每字符比较是一整词比较 $ O(L) $，树高 $ \log N $）；哈希表平均 $ O(L) $（哈希本身要读全串）但无前缀查询能力；Trie 查询 $ O(L) $ 且天然支持前缀/补全，是前缀敏感场景的最优解。

应用场景

  • 搜索引擎自动补全：输入前缀即时返回候选词，配合词频权重返回 Top-K
  • 拼写检查：编辑距离 1 的候选词集与 Trie 结合，快速找近似词
  • 敏感词过滤：标准 Trie 逐位置查询，或 AC 自动机单遍扫描多模式串
  • IP 路由最长前缀匹配：路由表前缀（如 192.168.0.0/16）用二叉/多位 Trie 查找
  • IDE 代码补全：变量名、函数名检索，前缀匹配毫秒级响应

Beam Search 解码

类别：NLP解码 | 难度：中等

算法简介

Beam Search（束搜索/集束搜索）是序列生成任务（机器翻译、文本摘要、语音识别、图像描述）中最经典的解码策略。它与贪心解码的本质区别是：贪心每一步只保留概率最高的 1 个候选 token，而 Beam Search 每一步保留概率最高的 $ k $ 个候选序列（$ k $ 即束宽 beam width），在"多条路径并行探索"和"计算成本"之间取得平衡。

可以把它理解为"保留多个备胎的贪心算法"：局部最优的第一步未必通向全局最优——例如概率 0.5 的 token A 开头后续路径整体概率很高，而第一步 0.7 的 token B 后面全是低概率词。Beam Search 通过同时跟踪 $ k $ 条这样的路径，显著降低"第一步选错满盘皆输"的风险。

每一步的流程是：将所有现存束（beam）分别扩展出词表的每个 token，计算每条扩展路径的累积对数概率，然后从所有扩展结果中选出全局最优的 $ k $ 条作为新束。当束生成 EOS（结束符）时，该束完成，移出活跃集。所有束完成后，按最终得分（常经长度惩罚调整）选出最优序列输出。

Beam Search 的工程要点集中在参数调优：num_beams（束宽）决定探索宽度，length_penalty（长度惩罚）纠正"模型偏爱短序列"的偏差，no_repeat_ngram_size 与 repetition_penalty 对抗重复循环，early_stopping 控制终止时机。

原理示意图

数学公式

1. 候选序列累积得分（对数概率）

$$ S(y_{1:T}) = \sum_{t=1}^{T} \log P(y_t \mid y_{1:t-1}, x) $$

变量解释：

  • $ y_{1:T} $：候选生成序列（$ y_1, y_2, \ldots, y_T $）
  • $ P(y_t \mid y_{1:t-1}, x) $：给定输入 $ x $ 与已生成前缀，第 $ t $ 步选中 $ y_t $ 的条件概率
  • $ \log $：将连乘转为连加以避免数值下溢（大量小概率相乘会溢出为 0）
  • 含义：序列联合概率的对数，因为 $ P(y_{1:T}) = \prod_t P(y_t|\cdot) $，取 log 后变加法

2. 长度惩罚后的最终得分

$$ \text{score}(y) = \frac{S(y)}{(T_y)^{\alpha}} $$

变量解释：

  • $ T_y $：候选序列 $ y $ 的长度
  • $ \alpha $：length_penalty 参数
  • $ \alpha = 1.0 $：标准长度归一化，长短序列公平比较
  • $ \alpha > 1.0 $：奖励长序列（分母变大反而让得分更高需注意符号——由于 $ S $ 为负，除以更大的数使负分变小、排序上升）
  • $ \alpha = 0 $：退化为不归一化，模型强偏好短序列
  • 含义：对数概率是负数累加，越长越负。若不除以长度，束搜索天然偏向"先碰到 EOS"的短序列

3. 每步保留束的选择

$$ \mathcal{B}_t = \text{top-}k\left(\{ (b, y) : b \in \mathcal{B}_{t-1}, y \in \mathcal{V} \}\right) $$

变量解释：

  • $ \mathcal{B}_t $：第 $ t $ 步保留的 $ k $ 条束的集合
  • $ b $：上一条束（含其累积得分）
  • $ y $：词表 $ \mathcal{V} $ 中的任意 token
  • $ \text{top-}k $：从 $ k \times |\mathcal{V}| $ 个扩展组合中选出累积得分最高的 $ k $ 个
  • 含义：束搜索每步是全局排序截断，不是每条束各自保留 top-k（这一点是常见误解）

4. 无重复 n-gram 约束

$$ \forall i \neq j: \quad (y_{i:i+n}) \neq (y_{j:j+n}) $$

变量解释：

  • $ y_{i:i+n} $：序列中从位置 $ i $ 开始长度为 $ n $ 的 n-gram 片段
  • $ n $：no_repeat_ngram_size 参数值
  • 含义：强制任意两个 n-gram 不相同，从候选生成阶段就阻断"短语复读"循环

核心要点

  • 与贪心的区别：贪心 = beam width 1，每步全局只留 1 条；Beam Search 留 $ k $ 条并行探索，抗"一步选错满盘输"
  • 得分是对数概率累加（防下溢），最终比较前必须做长度归一化/惩罚，否则强偏短句
  • num_beams 增大 → 质量提升但成本线性增长；1-4 常用于对话，4-8 常用于翻译/摘要
  • length_penalty > 1 缓解短句偏好；no_repeat_ngram_size=3~4 对抗重复循环
  • early_stopping=True 时任一束出 EOS 即整批停止；False 时所有束完成才停
  • 开放式生成（写小说/聊天）不适合 Beam Search：它倾向于高概率的"安全废话"（如 the the the），多样性差；适合有标准答案的任务（翻译/摘要/代码）

技术细节与参数详解

#### 参数1：num_beams（束宽 / beam width）

  • 含义：每一步保留的候选序列数量，是 Beam Search 最核心的参数
  • 类型：整数
  • 默认值：Hugging Face generate() 默认 1（即贪心）；翻译/摘要实践常用 4-8
  • 取值范围：1 到词表大小（实际 1-64）
  • 对结果的影响：
  • $ k=1 $：完全退化为贪心解码，最快但易陷入局部最优
  • $ k=4 $：翻译/摘要的甜点值，质量与速度平衡
  • $ k=8\sim16 $：闭集任务（语音识别、受限生成）进一步提升，但收益递减
  • $ k $ 每增大 1，每步候选扩展与排序成本增加约一倍（线性增长）
  • 推荐设置：机器翻译 4-5；文本摘要 4；语音识别 8-16；对话/创作类改用采样（top_p/temperature）而非加大束宽

#### 参数2：length_penalty（长度惩罚因子）

  • 含义：最终得分公式中的指数 $ \alpha $，得分除以 $ T^{\alpha} $，校正束搜索对短序列的系统性偏好
  • 类型：浮点数
  • 默认值：1.0（Hugging Face）
  • 取值范围：0 到任意正数（HF 允许负数但意义反转，慎用）
  • 对结果的影响：
  • $ \alpha=0 $：无归一化，极端偏短——第一个 EOS 就赢
  • $ \alpha=1 $：完全按平均每 token log 概率比较，长短公平
  • $ \alpha=1.2 $：温和奖励长序列，翻译常用（预期输出较长时）
  • $ \alpha=2.0 $：强推长序列，可能强行续写
  • 推荐设置：翻译/摘要 1.0-1.2；短答案任务（问答）0.8-1.0；若输出总被截断可增大；若输出冗长灌水可减小

#### 参数3：no_repeat_ngram_size（禁重复 n-gram 长度）

  • 含义：禁止生成序列中出现任何重复的连续 $ n $ 个 token 组合
  • 类型：整数，0 表示禁用
  • 默认值：0（HF）/ 3（部分摘要实践）
  • 取值范围：0 - 10
  • 对结果的影响：
  • $ n=3 $：最常见的防复读设置，拦截 "I like it, I like it, I like it" 类循环
  • $ n $ 过大（≥6）：合法的重复修辞（如排比句、代码中的常见结构）也被禁止，输出质量反降
  • $ n=0 $：不约束，重复风险由模型本身决定
  • 推荐设置：摘要/翻译 3；对话 2-3；代码生成慎用（语法要求重复 token，建议改用 repetition_penalty）

#### 参数4：repetition_penalty（重复惩罚）

  • 含义：对已生成过的 token 在下一步扩展时降低其 logit，抑制已经出现过的词再次出现（CTRL 论文提出）
  • 类型：浮点数
  • 默认值：1.0（不惩罚）
  • 取值范围：1.0 - 2.0（>1 惩罚；<1 鼓励重复，慎用）
  • 对结果的影响：
  • $ 1.0 $：无惩罚
  • $ 1.1\sim1.2 $：温和去重，对话常用
  • $ 1.3+ $：明显抑制重复，但可能连必要的功能词（the、的）也被压制，语句变怪
  • 推荐设置：与 no_repeat_ngram_size 二选一或小值并用；对话 1.1-1.15；代码生成不用（需要重复 token）

#### 参数5：early_stopping（提前终止）

  • 含义：控制"所有束完成"还是"部分束完成"即可停止
  • 类型：布尔/字符串
  • 默认值：False（HF 中 generate）
  • 取值范围：True / False / "never"（HF 新版）
  • 对结果的影响：
  • True：凑够 num_beams 条完成束即停，更快，但可能漏掉"起步慢后劲足"的序列
  • False：所有束都出 EOS 才停，更彻底，质量略稳但更慢
  • 推荐设置：生产翻译/摘要 True（速度优先）；离线评测 False（质量优先）

#### 参数6：max_length / max_new_tokens（生成长度上限）

  • 含义：解码的最大长度，防止束永不终止
  • 类型：整数
  • 默认值：HF 默认 max_length=20（很短！实际必须显式设置）
  • 取值范围：1 - 模型上下文长度
  • 对结果的影响：与 length_penalty 联动——上限太小会强制截断好束；上限太大配合 $ \alpha=0 $ 会偏向到顶才停
  • 推荐设置：翻译 128-256；摘要 64-128；务必显式设置，勿依赖默认值

#### 参数7：num_return_sequences（返回束数）

  • 含义：从最终 $ k $ 条束中实际返回多少条给调用方
  • 类型：整数
  • 默认值：1（只返回最优束）
  • 取值范围：1 - num_beams
  • 对结果的影响：设为 num_beams 可拿到全部候选（如后续用重打分模型挑选）；设 1 只拿冠军束
  • 推荐设置：一般 1；需要多候选重排（如 n-best 重打分）时等于 num_beams

#### 参数8：diversity 相关（num_beam_groups / diversity_penalty）

  • 含义：Diverse Beam Search——将 $ k $ 条束分成 $ g $ 组，组间通过 Hamming 多样性惩罚强制不同组探索不同方向
  • 类型：整数/浮点数
  • 默认值：禁用
  • 取值范围：num_beam_groups 整除 num_beams；diversity_penalty 常取 1.0-3.0
  • 对结果的影响：启用后候选束之间的相似度显著下降，适合"生成多个不同风格的候选"场景
  • 推荐设置：仅在需要多样化候选集（如数据增强、多方案生成）时启用；常规任务不用

一个最优候选不同，Beam Search 保留 num_beams 条候选路径并行探索……"""

inputs = tokenizer(article, return_tensors="pt", max_length=1024,

# 核心：Beam Search 生成（每个参数都有注释）
output_ids = model.generate(

# ===== 手写 Beam Search 核心逻辑（理解原理用）=====
import torch
import torch.nn.functional as F

def beam_search_decode(model, input_ids, num_beams=4, max_len=50,
                       length_penalty=1.0, eos_id=2):
    """手写 Beam Search：展示每步扩展-评分-截断全过程"""
    batch_size = input_ids.shape[0]                          # 批大小（简化为 1）
    # 初始化 k 条束：全部为输入序列的复制，累积 log 概率为 0
    beams = [(input_ids.clone(), 0.0)]                       # (序列, 累积得分)
    finished = []                                            # 已完成（出 EOS）的束
    for step in range(max_len):                              # 逐步解码
        candidates = []                                      # 本轮所有扩展候选
        for seq, score in beams:                            # 遍历每条活跃束
            logits = model(seq).logits[:, -1, :]             # 只取最后位置的 logits
            log_probs = F.log_softmax(logits, dim=-1)       # log-softmax 得对数概率
            topk_lp, topk_ids = log_probs.topk(num_beams)   # 该束只扩展概率前 k 的 token（工程剪枝）
            for lp, tok in zip(topk_lp[0], topk_ids[0]):   # 逐个候选 token
                new_seq = torch.cat([seq, tok.view(1, 1)], dim=1)  # token 拼接到序列尾
                candidates.append((new_seq, score + lp.item()))    # 累积得分 = 旧分 + 新 token log 概率
        # 全局排序取 top-k：注意是所有束的扩展一起排，不是每束各自保留
        candidates.sort(key=lambda x: x[1], reverse=True)
        beams = []                                          # 重建活跃束集合
        for seq, score in candidates[:num_beams]:          # 只留全局最优 k 条
            if seq[0, -1].item() == eos_id:                # 该束生成 EOS → 完成
                finished.append((seq, score))               # 移入完成池
            else:
                beams.append((seq, score))                  # 仍是活跃束
        if len(finished) >= num_beams:                      # early_stopping=True 的终止条件
            break                                            # 凑够完成束即停
    # 最终按长度惩罚得分挑选最优：score / T^α
    finished.sort(key=lambda x: x[1] / (x[0].shape[1] ** length_penalty),
                  reverse=True)                              # 除以长度^惩罚因子后排序
    return finished[0][0]                                   # 返回最优序列

复杂度分析

时间复杂度：每步扩展 $ k $ 条束 × 每束取 top-k 候选（$ O(|\mathcal{V}|\log k) $ 堆选择），生成 $ T $ 步：

$$ T_{\text{beam}} = O(T \cdot k \cdot |\mathcal{V}|) $$

  • 变量：$ k $=num_beams，$ T $=生成长度，$ |\mathcal{V}| $=词表大小
  • 对比贪心：$ O(T \cdot |\mathcal{V}|) $，Beam Search 是它的 $ k $ 倍

空间复杂度：$ O(k \cdot T) $ 存储 $ k $ 条束各自最长 $ T $ 个 token；加上 KV Cache 则为 $ O(k \cdot T \cdot d \cdot L) $（$ d $=隐藏维度、$ L $=层数），这也是大束宽吃显存的原因。

收益递减规律：$ k $ 从 1→4 质量提升明显，4→10 提升放缓，10 以后在开放式任务上反而下降（高概率=平庸），因此不建议盲目堆束宽。

应用场景

  • 机器翻译：Beam Search 的经典主场，num_beams=4-5 是学术标准配置
  • 文本摘要：BART/T5 类模型标配，配合 length_penalty 控制摘要长度
  • 语音识别（ASR）：beam 8-16 + 语言模型重打分，显著降 WER
  • 图像描述生成：CNN+LSTM 时代标配解码，现多用于评测对比
  • 受限代码生成：有明确正确性目标的生成（SQL、函数补全）比纯采样更稳

思维树 Tree-of-Thought

类别：大模型推理 | 难度：困难

算法简介

Tree-of-Thought（ToT，思维树）是普林斯顿大学团队 2023 年在 NeurIPS 上提出的 LLM 推理框架，核心思想是：将大模型的"思维生成能力"与传统 AI 的"树形搜索算法"结合，模拟人类解决复杂问题时的深思熟虑过程——多路径探索、动态评估、必要时回溯重来。

传统推理范式的局限是线性的：IO prompting 直接问直接答；CoT（思维链）虽然分步推理，但只有一条路走到黑——一旦中间某步推理失误，后面全部建立在错误之上，且无法回头。ToT 则把推理过程组织为一棵树：每个节点是一个"思维状态"（thought state，即一段连贯的中间推理步骤），LLM 在每个节点生成多个候选想法（分支），由 LLM 自身担任"评估器"为每个状态打分（sure/likely/impossible），再配合 BFS/DFS 搜索策略在树上探索：保留有前途的分支、放弃无前途的分支、必要时回溯到上一层换路径。

这带来两个关键能力突破：前瞻（look ahead）——评估当前想法能否通向好的未来；回溯（backtrack）——发现死路后回头换路。在 24 点游戏、创意写作、填字谜题三大基准上，GPT-4 配合 ToT 的成功率从 CoT 的约 4%（24 点）跃升至 74%，是提示工程领域最具影响力的推理框架之一。

原理示意图

数学公式

1. 思维状态与转移（树形化推理）

$$ s_{t+1}^{(i)} = \text{LLM}_{\text{gen}}(x, s_1, s_2, \ldots, s_t), \quad s_{t+1}^{(i)} \in \mathcal{C}(s_{1:t}) $$

变量解释：

  • $ x $：原始问题输入
  • $ s_t $：第 $ t $ 步的思维状态（一段中间推理，非单个 token）
  • $ s_{t+1}^{(i)} $：第 $ t+1 $ 层的第 $ i $ 个候选想法
  • $ \mathcal{C}(s_{1:t}) $：给定当前部分解的所有可能下一步想法集合
  • $ \text{LLM}_{\text{gen}} $：负责"提出候选想法"的模型调用（采样 $ k $ 个不同想法）
  • 含义：与 CoT 一步只产一个 token 不同，ToT 每步产出 $ k $ 个完整思维片段候选

2. 状态评估函数（LLM 自评）

$$ V(s_{1:t}, x) = \text{LLM}_{\text{eval}}(x, s_{1:t}) \in \{\text{sure}, \text{likely}, \text{impossible}\} $$

变量解释：

  • $ V $：评估函数，给"当前部分解"打分
  • $ \text{LLM}_{\text{eval}} $：同一个 LLM 扮演评估者，判断该思维状态的前途
  • sure：有信心，优先扩展；likely：有希望，可继续；impossible：无望，剪枝
  • 含义：LLM 既当"生成者"又当"评估者"，无需训练额外价值网络（区别于 MCTS 中的已学习 evaluator）

3. 搜索目标（寻找最优思维路径）

$$ y^* = \arg\max_{s_{1:K}} \prod_{t=1}^{K} P(s_t \mid x, s_{1:t-1}) \cdot V(s_{1:t}) $$

变量解释：

  • $ y^* $：最终输出的最优解路径（从根到某叶的完整思维链）
  • $ K $：树的深度（问题分解步数）
  • $ P(s_t \mid \cdot) $：生成器给该想法的采样概率（用于采样多样性）
  • $ V(s_{1:t}) $：评估器对路径的评分（用于剪枝与选择）
  • 含义：ToT 的目标是找到"生成概率与评估得分综合最优"的完整推理路径

4. 剪枝条件（DFS 回溯触发）

$$ \text{prune}(s_{1:t}) \iff V(s_{1:t}, x) = \text{impossible} \lor \text{budget}(s_{1:t}) \geq B $$

变量解释：

  • $ \text{prune} $：剪枝操作（放弃当前分支，回溯到父节点）
  • $ V=\text{impossible} $：评估判定无望
  • $ \text{budget}(\cdot) $：当前分支已消耗的 LLM 调用/步数
  • $ B $：预设搜索预算（防止无限扩展）
  • 含义：两个剪枝触发条件：评估判死，或预算耗尽；触发后回溯换兄弟分支

5. 与 CoT 的能力对比（24 点游戏）

$$ \text{成功}$(CoT) \approx 4\% \quad \ll \quad \text{成功}(\text{ToT}) \approx 74\% $$

变量解释：成功率基于 GPT-4 在 Game of 24 基准上的实测：CoT 仅 4%，ToT 达 74%，提升约 18 倍。含义：在需要搜索、试错、回溯的规划类任务上，树形推理对线性推理的优势是压倒性的。

核心要点

  • 核心公式化：ToT = 思维分解（大步 reasoning）+ 每节点多候选想法 + LLM 自评 + BFS/DFS 树搜索 + 回溯剪枝
  • 与 CoT 的本质区别：CoT 是"单链不可回头"，ToT 是"树形可评估可回溯"，模拟人类深思熟虑
  • LLM 一角三用：生成器（出想法）、评估器（打分剪枝）、汇总器（终局比较），全程免训练、纯提示实现
  • 评估三档制（sure/likely/impossible）是关键工程设计：粗粒度打分比细粒度数值更稳，LLM 自评噪声更小
  • 24 点游戏上 GPT-4 从 CoT 4% → ToT 74%，创意写作与填字同样大幅超越
  • 成本代价显著：LLM 调用次数是 CoT 的数十倍以上，适合高价值难题，不适合普通问答
  • 后续演进：GoT（图思维，节点可合并）、MCTS 变体（AlphaZero 式树搜索+价值网络）、ToT 简化版（BoT 分层检索）

技术细节与参数详解

#### 参数1：thought decomposition（思维分解粒度）

  • 含义：每个思维节点包含的推理步大小——是"一句话想法"还是"一段推理"，决定树的形态
  • 类型：策略枚举
  • 默认值：视任务定：24 点用一步（一个算式）、创意写作用一段（一个段落草稿）
  • 取值范围：单词级 / 短句级（1-2 步）/ 段落级（几步） / 完整方案级
  • 对结果的影响：
  • 粒度太细（token/词级）：树深且分支爆炸，评估失去语义（单 token 难以评估前途），退化为昂贵版搜索
  • 粒度太粗（整段级）：步数少，但单步生成质量压力大，一次失误整段报废
  • 推荐设置：让"一个思维"= 可被独立评估的最小有意义单元：数学题一步运算；作文一段草稿；代码一个函数设计

#### 参数2：k / num_candidates（每节点候选想法数）

  • 含义：每个思维状态下采样生成多少个候选下一步想法（分支因子 branching factor）
  • 类型：整数
  • 默认值：论文中 BFS 用 $ k=1\sim5 $，DFS 常用 3-5
  • 取值范围：1 - 20
  • 对结果的影响：
  • $ k=1 $：无分支，退化为 CoT（失去 ToT 意义）
  • $ k=3\sim5 $：兼顾多样性与成本，多数任务甜点值
  • $ k $ 过大：候选间相似度高（都是模型"舒适区"想法），成本线性上升收益小
  • 推荐设置：3-5 起步；若发现候选想法高度雷同，改用高 temperature 采样增强多样性

#### 参数3：search strategy（搜索策略 BFS/DFS）

  • 含义：在思维树上遍历的顺序——逐层展开还是深入到底再回头
  • 类型：枚举
  • 默认值：论文按任务选择：创意写作（浅树）用 BFS；24 点/填字（深树）用 DFS
  • 取值范围：BFS / DFS / 束式（beam over states）
  • 对结果的影响：
  • BFS：每层全评估后进下一层，适合"层数少、每步大"的任务；内存持有整层状态
  • DFS：一条路走到死路再回溯，适合"层数多、每步小"的任务；内存只需当前路径
  • 推荐设置：问题分解浅（≤3 层）选 BFS；深（≥4 层）选 DFS 或 DFS+剪枝预算

#### 参数4：evaluation strategy（评估方式）

  • 含义：LLM 对每个思维状态打分的形式
  • 类型：枚举
  • 默认值：三档分类（sure/likely/impossible）—— 论文默认
  • 取值范围：
  • 三档分类（value 样本内打分）
  • 数值打分（1-10 分）
  • 两两比较（pairwise compare，多个状态互相比出最优）
  • 对结果的影响：
  • 三档制：稳定、成本低，粗粒度反而降低 LLM 自评噪声
  • 数值制：细粒度但噪声大（同一状态多次打分分差大）
  • 两两比较：最准但调用次数平方级增长，仅小候选集可用
  • 推荐设置：默认三档制；对最终候选挑冠军时可用两两比较精调

#### 参数5：b（每层保留状态数，BFS 用）

  • 含义：BFS 每层评估后保留多少个最有希望的思维状态进入下一层
  • 类型：整数
  • 默认值：论文创意写作用 $ b=1\sim2 $
  • 取值范围：1 - k
  • 对结果的影响：$ b $ 越大保留越多样、探索越广、成本越高；$ b=1 $ 退化为"每层只留冠军"的链式推理（但仍有跨层评估与重启）
  • 推荐设置：浅树任务 $ b=1\sim2 $ 即可；并行预算充足可加到 3-4

#### 参数6：B / search budget（搜索预算）

  • 含义：单问题允许的最大 LLM 调用次数/节点扩展数，是剪枝与终止的硬约束
  • 类型：整数（调用次数）
  • 默认值：论文 24 点实验约 100 次节点访问
  • 取值范围：数十到数百
  • 对结果的影响：预算太小→早停错过解；太大→成本失控（ToT 本就比 CoT 贵 10-100 倍）
  • 推荐设置：离线难题求解 100-200；在线交互式场景 20-50 并配强剪枝

#### 参数7：temperature（生成多样性温度）

  • 含义：采样候选想法时的温度——影响候选想法之间的差异度
  • 类型：浮点数
  • 默认值：论文用 0.7-1.0（需要多样性）
  • 取值范围：0 - 1.5
  • 对结果的影响：温度太低（<0.3）候选想法趋同，k 个分支形同虚设；太高（>1.2）想法发散但质量参差，评估负担加重
  • 推荐设置：候选生成 0.7-1.0；终局比较/评估时降为 0（要稳定）

#### 参数8：prompt 模板设计（propose prompt vs evaluate prompt）

  • 含义：两类提示词的设计质量直接决定 ToT 效果：propose prompt（生成候选想法）与 evaluate prompt（评估状态前途）
  • 类型：文本模板
  • 默认值：论文为每任务手写（无通用默认）
  • 取值范围：任意提示工程方案
  • 对结果的影响：propose prompt 决定"想法空间覆盖度"（是否提示"给出 k 个不同"会显著增加多样性）；evaluate prompt 决定剪枝准确率（示例 few-shot 评估比零样本评估更稳）
  • 推荐设置：propose prompt 明确要求"k 个不同且相互独立"的想法；evaluate prompt 提供 sure/likely/impossible 的判断标准与示例

代码示例

import openai                    # 导入 OpenAI SDK（ToT 仅需普通 LLM API，无需训练）
from typing import List, Optional  # 类型注解
import math                      # 数学工具


# ============ 思维状态节点 ============
class ThoughtNode:
    """思维树节点：一个'思维状态'= 到此为止的完整推理路径"""
    def __init__(self, state: str, parent=None):
        self.state = state       # 当前思维内容（如 "2+8=10"）
        self.parent = parent     # 父节点（回溯的关键）
        self.children = []       # 子节点列表
        self.value = None        # 评估得分（sure/likely/impossible）
        self.visited = False     # DFS 用：是否已扩展过

    def path(self) -> List[str]:
        """从根到当前节点的完整思维路径（回溯输出解时用）"""
        if self.parent is None:  # 根节点
            return [self.state]
        return self.parent.path() + [self.state]  # 递归拼接父路径


# ============ ToT 主类 ============
class TreeOfThoughts:
    """Tree-of-Thought 推理框架（DFS 实现，24 点游戏示例）"""

    def __init__(self, client, model="gpt-4",
                 num_candidates=5,       # k：每节点候选想法数（分支因子）
                 max_depth=4,            # 树深上限（问题分解步数）
                 budget=100):            # 搜索预算（LLM 调用上限）
        self.client = client             # LLM API 客户端
        self.model = model               # 使用的模型
        self.k = num_candidates         # 分支因子 k
        self.max_depth = max_depth       # 最大深度
        self.budget = budget             # 预算
        self.calls = 0                  # 已消耗调用数

    def _chat(self, prompt: str, temperature=0.7) -> str:
        """LLM 调用封装（统一计数预算）"""
        self.calls += 1                  # 预算计数
        resp = self.client.chat.completions.create(
            model=self.model,            # 模型名
            messages=[{"role": "user", "content": prompt}],  # 用户消息
            temperature=temperature,     # 温度：候选生成用高值保多样性
        )
        return resp.choices[0].message.content  # 返回文本

    def propose(self, problem: str, path: List[str]) -> List[str]:
        """生成器：给定问题与已走路径，提出 k 个候选下一步想法"""
        path_str = "\n".join(f"Step {i+1}: {s}" for i, s in enumerate(path))  # 格式化路径
        prompt = f"""You are solving: {problem}
Current reasoning so far:
{path_str}

Propose {self.k} DIFFERENT possible next steps.
Each step should be a short, self-contained thought (one operation for math).
Output exactly {self.k} numbered candidates, one per line."""     # 要求相互独立、互不重复
        out = self._chat(prompt, temperature=0.9)  # 高温度采样保证分支多样性
        lines = [l.strip().lstrip("0123456789. ") for l in out.strip().split("\n") if l.strip()]
        return lines[:self.k]         # 解析出 k 个候选想法

    def evaluate(self, problem: str, path: List[str]) -> str:
        """评估器：判断当前思维路径的前途（三档制）"""
        path_str = "\n".join(f"Step {i+1}: {s}" for i, s in enumerate(path))
        prompt = f"""Problem: {problem}
Reasoning so far:
{path_str}

Evaluate whether this partial reasoning can lead to a correct final answer.
Reply with exactly one word:
- sure: promising, continue
- likely: might work
- impossible: dead end, should backtrack"""
        out = self._chat(prompt, temperature=0)  # 评估用温度 0 保证稳定
        for tag in ["sure", "likely", "impossible"]:  # 解析三档结果
            if tag in out.lower():
                return tag
        return "likely"               # 解析失败降级为 likely

    def solve(self, problem: str) -> Optional[List[str]]:
        """DFS 求解主入口：带评估剪枝与预算控制"""
        root = ThoughtNode("")         # 根节点（空思维）
        return self._dfs(problem, root, [], 0)  # 从根开始 DFS

    def _dfs(self, problem, node, path, depth):
        """DFS 递归：扩展-评估-剪枝-回溯"""
        if depth >= self.max_depth:    # 达到深度上限 → 终局判断
            return self._terminal_check(problem, path)  # 是解则返回路径
        if self.calls >= self.budget:  # 预算耗尽 → 剪枝（防成本失控）
            return None
        for idea in self.propose(problem, path):  # 生成 k 个候选想法
            new_path = path + [idea]   # 拼接新路径
            verdict = self.evaluate(problem, new_path)  # LLM 自评
            if verdict == "impossible":  # 判死 → 剪枝，试下一个兄弟
                continue                 # 跳过该分支（等价于回溯换路）
            child = ThoughtNode(idea, node)  # 建子节点
            node.children.append(child)        # 挂到树上
            result = self._dfs(problem, child, new_path, depth + 1)  # 深入递归
            if result is not None:      # 子树找到解 → 直接向上传播
                return result
            # 子树无解 → 自然回溯，继续 for 循环试下一个兄弟想法
        return None                      # 所有候选都失败 → 向上返回 None（回溯）

    def _terminal_check(self, problem, path):
        """终局检查：叶子节点是否为有效完整解"""
        path_str = "\n".join(f"Step {i+1}: {s}" for i, s in enumerate(path))
        prompt = f"""Problem: {problem}
Complete reasoning:
{path_str}

Is this a correct and complete solution? Answer YES or NO."""
        out = self._chat(prompt, temperature=0)  # 零温度判断
        return path if "YES" in out.upper() else None  # 是解返回路径，否则回溯

复杂度分析

LLM 调用次数复杂度（ToT 的真正"复杂度"不是计算而是 API 调用成本）：

$$ C_{\text{ToT}} = O\left(\sum_{d=1}^{D} b^{d} \cdot k \cdot c\right) $$

变量解释：

  • $ D $：树的深度（思维分解层数）
  • $ k $：每节点候选想法数
  • $ b $：每层实际保留的状态数（BFS）
  • $ c $：每状态评估所需调用数（三档制 $ c=1 $；两两比较 $ c=\binom{k}{2} $）
  • 含义：DFS 最坏情况 $ O(k^D) $（全不剪枝），实际因评估剪枝远低于此；论文 24 点平均约 100 次调用

对比 CoT：CoT 恒为 1 次调用；ToT 是它的数十到数百倍。这是 ToT 的核心权衡：用推理时的计算量换准确率——属于 "test-time compute scaling" 思想的代表工作。

空间复杂度：BFS 需持有整层状态 $ O(b \cdot k \cdot |s|) $（$ |s| $ 为单状态文本长度）；DFS 仅需当前路径 $ O(D \cdot |s|) $ 加已存子树。

应用场景

  • 数学推理与谜题：24 点、数独、逻辑谜题——需要试错与回溯的搜索密集型任务
  • 创意写作：段落级计划多方案并行起草、评估、择优、展开
  • 复杂规划与决策：Agent 任务分解（先探索多套计划，评估后选定一套执行）
  • 代码架构设计：对同一需求生成多套设计思路，评估可行性后细化最优方案
  • 科研假设探索：多假设并行推演，剪枝无望方向（如 GoT 图思维进一步支持假设合并）
